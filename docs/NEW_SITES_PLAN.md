## 5. 红线判据（新增一条可复用的）

> **用本机真 Chrome（headed）跑一次目标章节页。仍被挡 → 属「给人的验证码」→ 不做。**
> 能与不能的分界：**给浏览器的 JS 挑战**（Qidian 的 Chaos VM、阿里云 WAF `acw_*`）→ 真浏览器执行即过；
> **给人的图形验证码**（刺猬猫的 geetest `/signup/man_machine_verify`）→ 真浏览器也挡。

**不做清单（本批明确排除）**：
1. 人机验证（刺猬猫已判）；
2. 登录墙 / 凭据流程（第 6 层代码自检本就拦）；
3. **付费墙绕过**——例如前端覆写 VIP 状态（`pageData.vipInfo.isVip = 1` 之流，`youjian` 项目就是这么干的）；
4. 破解服务端加密正文（若无合法可取路径，记账后放弃）；
5. **不新增盗版镜像站**（现有 3 条足够；边际价值低、法律风险高）——除非你明确要求。

### 9.1 一条重要的方法论更正

第三轮开头我据「首页 200、章节页 200、最大中文元素 697 字」判**寒武纪年「可直接做」**——
**是错的**：697 字是**元信息**（章节名 + 字数 + 书评），不是正文。

**判断「正文是否在 HTML 里」的正确做法**：
1. 拿**章节声明的字数**（页面上的「字数:2623字」）与实际可取文本量做**数量级对比**；
2. 检查有没有**正文接口调用**（浏览器网络日志 / 页面 JS 里的 ajax）。

只看「页面能打开 / 有中文」必然误判。这条已写进 `docs/FREE_ONLY.md` 与技能。

### 11.2 新增的两个通用能力（都是「治本」，不是为单一站点打补丁）

**A. 等待条件按页面角色声明**（`browser.wait_selector` 支持对象写法）

发现路径：速读谷探测定时 37s，其中 **30s 是纯浪费**。根因不是速读谷，而是
**顶层 `browser.wait_selector` 是「全角色广播」** —— 把章节容器 `div.con` 写成顶层字符串后，
**书籍页**也去等 `div.con`（那里根本没有）→ 白等满 30 秒超时。

```json
"wait_selector": {"chapter": "div.con"}   // ✅ 只作用于章节页 → 37.0s 降到 7.6s
"wait_selector": "div.con"                // ❌ 书籍页/目录页一起遭殃
```

同病的 `soushuwang.cc`（`#chaptercontent`）一并改掉。⚠ qidian 的顶层字符串是**书籍页**条件
（`#bookName`），改造后必须仍在 —— 已加回归测试守住。

**B. 导航瞬时失败的重试必须带退避**

这类站抽风**不是单次抖动，而是一段时间内持续 reset** —— 实测速读谷：
0 退避连发 3 次重试 → **三次全 `ERR_CONNECTION_RESET`**；加 `1.2s × n` 退避后
**首个重试即成功**。故新增 `browser.nav_retries`（1~8，默认 **4**），间隔 `1.2s × 第几次`。
这与全哥的判断一致：「**抽风是盗版网站通病**」→ 对策是重试 + 断点续爬，
**不要凭一次失败判死**。

**C. 顺手修掉潜伏 bug：`catalog.browser_wait_selector` 从未生效**

该字段写在 `catalog` 段下（文档也是这么写的），但代码读的是 `catalog.pages` 子字典
（`cfg = rule.catalog_cfg.get("pages")`）→ **恒为 None**。于是 17K 声明的目录等待条件
一直靠 `wait_ms: 2500` 掩盖着、**从未真正启用**（属于「配了但没接线」）。已修，
实测 17K 目录 586 章 / 13.3s、正文 114 段 2311 字，无回归。

### 11.3 书源库进入规划（P2，本轮不实施）

**定位：把社区书源库当作「候选站点线索池」，绝不是可直接运行的规则源。**

**为什么不直接适配**

书源格式是「阅读」APP（Legado）的规则 JSON —— `ruleSearch` / `ruleBookInfo` / `ruleToc` /
`ruleContent`，配 `{{}}` 变量、`@css:` / `@XPath:` 前缀、甚至内联 JS 与 `java.*` 调用。
它与本项目 schema（`book` / `catalog` / `chapter` + 归一化管道）**没有交集**；
更关键的是书源普遍**内置搜索接口、多源聚合、并发调度**，并大量依赖 APP 运行时。
全哥的定性已经很清楚：**「书源服务于阅读 APP，其他应用不适配，仅作为参考」**。

**许可与合规（硬约束）**

- 「阅读」APP **已删除开源源码**并公告：本项目涉及侵权行为违法、也为此承担了相应法律责任。
- 故本项目：**不复制其源码、不 vendoring 书源 JSON 进仓、不随仓分发**。
  与 `docs/REFERENCE.md` 既有机制一致 —— 只记「来源链接 + 用途（线索）+ 不入仓声明」，
  并由 `tools/check_repo.py` 第 2 项（无第三方源码目录）与第 6 项（借鉴记账完整）机械校验。
- 书源 JSON 本身多为社区贡献、无明确许可证 → 一律按**不入仓**处理。

**怎么用（三步，本轮只规划）**

| 步骤 | 做什么 | 已有工具 |
|---|---|---|
| 1 **取线索** | 从书源库索引（`shuyuan.yiove.com/book-sources`、Gitee `xioo/shuyuan`、`XIU2/Yuedu`）导出「站点名 + 域名 + 是否需登录/搜索接口」清单。**只取域名与主页链接，不取规则体** | 缺（需新写一个纯标准库小工具） |
| 2 **过筛** | 域名级去重（现有 20 条规则：正版 13 / 免费镜像 7）→ 过 §1 准入门槛（免费可读 / 无需登录 / 无 captcha 红线） | `noveldown sites` |
| 3 **实探** | 对通过初筛的域名**批量实探**（抓目录 + 抽 1 章 + 报字数），**用实测结果**决定是否写规则 | ✅ 已有 `tools/probe_site.py` |

⚠ **不凭书源里的选择器直接写规则** —— 书源里的 `#list li a` 之类只能当**起点假设**，
必须用本项目的实探结果确认（速读谷就是好例子：书源给的选择器基本对，但
「书名不能用 `h1`」「目录是新章在前」这两点只有实探才能发现）。

**预期收益 / 成本 —— 以及一次被全哥纠正的判断**

- **收益**：候选池从「手工搜到的十几个」扩到「上万个书源对应的站点」。
- ⚠ **我原先写在这里的结论是错的**（原文：「边际价值在下降……新增站大概率是同一套模板的
  又一个镜像 → 记为 P2、先不做」）。全哥纠正：
  > 「盗版尽量铺开镜像站数量，**不能因为是大概率是同一套模板的又一个镜像而跳过**。
  > 这就是**要分开建池的原因**。盗版站存在抽风通病，**源越多才能更好规避**。」

  这条判断是对的，而且它同时解释了两件事：
  1. **为什么必须分池**：镜像站的价值不在「模板新」，而在「**同类源的数量**」——
     同一个模板的 N 个镜像互为备份，单站抽风时整体仍可用。
     所以池子的意义是「**可替换的等价源集合**」，不是「来源分类标签」。
  2. **为什么"同模板"不是跳过理由**：判据是「**这份备份能不能用**」，不是「它新不新」。
     （同一个错误我之前犯过两次：按「含 VIP」整站拉黑、按「标签」丢技术 —— 见 skill §1.7 / §1.9。
     这是第三次，形态是**按"信息增量"否决"可用源"**。）

- **成本**：两个批量工具（线索采集 + 存活/结构扫描）+ 生成族规则 + 逐族抽样验证。

**本轮（v1）实际做法与验收标准**

| # | 步骤 | 产出 |
|---|---|---|
| 1 | 从书源库拉**元数据**（只有 name/url/热度，**不拉规则体**） | `tools/harvest_book_sources.py` → `.sources/shuyuan.jsonl`（不入仓） |
| 2 | 按域聚合 + 启发式剔除（正版/论坛漫画有声/成人向），按热度排序 | 同上 |
| 3 | **存活扫描**（DNS 预筛 + HTTP，1 请求/站） | `.sources/live.jsonl` |
| 4 | **结构扫描**（书籍页→目录→抽 1 章，逐个候选选择器**实测**） | `.sources/deep.jsonl`，每站记「命中的目录/正文选择器」 |
| 5 | 按「命中选择器组合」聚类 → 生成族规则，`match` 只收**实测通过**的域 | `noveldown/rules/*.json` |
| 6 | 逐族**抽样验证**（`probe` + 抽 1~2 个域跑 `fetch --limit`） | 验证记录 |

硬性约束（延续 §11.3 原有约定）：

1. 工具**不把任何书源 JSON / 规则体写入仓库**（原始清单落 `.sources/`，已 gitignore）。
2. 每个域必须有**实测结论**才写进 `match`：`可做`（附目录数/正文字数）/ `红线` / `不可达`。
   **不允许**因为「和已接入站同模板」就直接写进去。
3. `tools/check_repo.py` 兜底：产物若含书源规则体，门禁必须 **FAIL**。
4. 域进 `match` 后，**族规则仍需可用**——抽样验证覆盖每个新族规则，不靠"看起来像"。

### 12.2 预判的难点（先写下来，避免实探时重复踩）

1. **APP 优先 → 网页端可能只有试读**。番茄/七猫的教训：web 端"付费章"其实是
   **APP 独占**，正文被替换成「请下载 APP」引导语（该引导语**有 78 字**，会骗过最小字数阈值）。
   → 判据：`PAYWALL_MARKERS` 要覆盖 `下载【`/`APP内免费畅读`/`扫码下载`（已实现）。
2. **登录墙是红线**，且**必须用真浏览器会话复测**才能定性：
   页面能打开、目录接口甚至开放，但正文接口恒 `code:401`（息壤的形态）。
3. **反爬令牌 ≠ 人机验证**：大厂站多为「给浏览器的 JS 挑战」，属可做
   （真 Chrome + headed + 关 AutomationControlled）；只有图形验证码才是红线。
4. **别用单一 HTTP 客户端判死**（curl 000 而 requests 200 的实测教训）。

#### （3）浏览器路由的「拆除税」：占总耗时 90% 的空转

做「已接入站做深」时顺手量了一次端到端，结果最刺眼的一项跟站点无关：

| 阶段 | 实测（豆瓣专栏，反检测路由） |
|---|---|
| 启动 BrowserFetcher | 2.3 s |
| `new_page()` + `goto(domcontentloaded)` | 1.1 s |
| `wait_for_selector(a.chapter-item)` | 1.0 s |
| `wait_ms` | 4.0 s |
| `page.content()` | 0.1 s |
| **`close()`** | **58.5 s** ← 拆到 `browser.close()` 独占 **47.8~50.4s** |

也就是：**一次 3 章的抓取，61.9 秒里有 58.5 秒在关浏览器。**

试过的拆除路径（同一台机器，反检测路由）：

| 路径 | 耗时 | 残留 playwright 子进程 |
|---|---|---|
| `ctx.close()` + `browser.close()` + `pw.stop()` | 0.0 + 50.4 + 0.1 = **50.5s** | 0 |
| `ctx.close()` + `pw.stop()` | 0.0 + **36.0s** = 36.0s | 0 |
| headless 捆绑内核 + `browser.close()` | **20.6s** | 0 |
| 直接 `os._exit(0)`（不拆除） | **6.9s** | **1（12 秒后仍在 = 泄漏）** |
| **杀本实例进程树 + `pw.stop()`** | **0.00 + 0.04 = 0.04s** | **0** ✅ |

采纳最后一条。**安全边界**（这是项目里唯一会主动结束他人进程的地方）：
只杀**本进程的后代**，且 cmdline 必须命中本实例特征
（Playwright 专属临时 profile `playwright_chromiumdev_profile-XXXX` / `run-driver`）
—— 用户自己开的 Chrome 既不在这个进程树里、也不带这个 profile。
没装 psutil 或特征不符就**退回优雅拆除**；`NOVELDOWN_NO_FAST_CLOSE=1` 可整体关掉。
6 条单测锁住这些边界（含「识别特征不得宽到 `chrome`/`node`」）。

**效果**：豆瓣专栏 **75.8s → 13.3s**；起点 1418 章取前 3 章 **30.0s**、1265 章 VIP 零请求。

#### （5）红袖/小说阅读网「标题重复」结案：**是站点命名，不是抓取缺陷**

实测《重生换宗，小可怜被大佬们团宠了》（316 章全免费）：

| 章节 | cid | 标题 | 正文 |
|---|---|---|---|
| #313 | 93156500419167332 | 番外：归家 | 169 字，首段「修仙界某处雪原」 |
| #315 | 93226180341200923 | 番外：归家 | 182 字，首段「妇人先是一愣…」 |

**两章正文重合度 1%**（内容完全不同）→ 站点自己有两个番外撞了名。
**不做去重**（去重会删掉一章真内容）；改的是报告的**定性**：

- 同名 + 同文 → `duplicate_title`（真重复，回显块/重复抓取）
- 同名 + 不同文 → 新增 `title_clash`，**不计入阻断项**，报告里写明「站点命名，不是抓取缺陷，不清除」
- 有一侧正文未取到（`--limit`/受保护）→ `body_same: None`，判「未定」，不硬下结论

复验：红袖 316 章 → 「标题重复 0 · 标题同名 1」，条目为
`#315 「番外：归家」与 #313 同名，正文已确认不同`。

> ⭐ **可复用的判据**：**「同名」不是缺陷，「同名且同文」才是。**
> 凡是"看起来像重复"的信号，先问一句「两条的**内容**是否真的相同」再下结论 ——
> 否则最坏情况是**修掉一个不存在的问题，同时删掉真数据**。

#### （3）⚠ 一条会**静默出错**的红线级问题（本轮最重要的发现）

**付费章走正文接口既不报错、也不给任何付费提示**，只返回一段**戛然截断的试读片段**：

| 章 | `paid` | `unlock` | 接口返回正文 |
|---|---|---|---|
| 第 1 章 | `0` | `true` | **2392 字符 / 1658 汉字**（完整） |
| 第 11 章 | `2` | `false` | **642 字符 / 434 汉字**（试读，**无任何付费字样**） |

也就是说：**第 4 层「正文付费墙特征词」在这一站完全失效**。
它不报错、不提示，正文就是正常文字然后突然结束 —— 只靠它会把试读片段
**当正文静默导出**，而且导出物里看不出来。

**修法（两道独立防线）**：
- **第 3 层**：`catalog.json.vip_field = op_ext.money_topic.paid` +
  `vip_truthy = ["1","2"]` → 480 章在**目录层**判 locked，**零请求**；
- **第 4 层加强**：`chapter.body_api.require = {"field": "data.unlock"}` →
  正文接口回 `unlock: false` 即判 **blocked、不导出**。这道**不依赖正文里有没有特征词**。

> ⭐ **可复用判据**：**判"能不能免费拿"要优先看数据源的权威字段，而不是正文里有没有标记。**
> 凡是「接口同时下发正文与付费状态」的站点，`require` 比特征词可靠得多 ——
> 试读片段、截断正文、水印段这些形态都**不会**在正文里自我声明。

#### （4）顺带修掉终检工具的一个真实缺陷

`tools/verify_artifacts.py` 拿**受保护章节的标题**去正文里搜来判「零泄漏」，
而该书第 490 章的标题**就是一个字「番」** —— 单字在正常正文里必然出现 → **必然误报**。
→ 修法：标题短于 **4 字**的不作泄漏判据，并**显式列出被跳过的短标题**（不静默放宽）。
**已反证**：注入一个**长**的受保护标题后仍然 FAIL，判据没有被削弱。

## 13.2 虚阁网实测（2026-09-21，本轮）

**站点性质**：大型中文出版书文本库。首页 10 个一级分类：

**⚠ 本轮最重要的新发现：编码是「逐页级」的，同一站点内不统一**

实测 8 个 URL（2026-09-21 二次复核，修正了先前「按分区不同」的粗结论）：

| URL | HTTP header | meta | 强制 gb18030 |
|---|---|---|---|
| `/wgwx/index.htm` | `UTF-8-SIG` | `utf-8` | ❌ 全乱码 |
| `/wgwx/cxs/index.htm` | `GB2312` | `gb2312` | ✅ 正确 |
| `/wgwx/zpj/index.htm` | `GB2312` | `gb2312` | ✅ 正确 |
| `/xdwx/index.htm`、`/ls/index.htm` | `UTF-8-SIG` | `utf-8` | ❌ 全乱码 |
| `/gdwx/index.htm`、`/gdwx/hlm/index.htm`、`/xdmj/hushi/twrj/index.htm` | `GB2312` | `gb2312` | ✅ 正确 |

**注意同一分区 `wgwx/` 里既有 utf-8 页也有 gb2312 页** —— 所以「按分区固定编码」也不成立。

→ **只能按每个响应自己的 header/meta 解码**（`requests` 的 `resp.text` 实测 **8/8 正确**）。
**胡适日记项目「统一按 GB18030 解」的做法不能照搬** —— 它只适合它碰过的那几页 gb2312。
⚠ 乱码指纹：`澶栧浗鏂囧` —— 「是汉字但不成词」，一眼可辨。

**形态可跑性（用真实入口验证，非推测）**

```python
book.url_pattern = r"^https?://www\.xuges\.com/([a-z0-9_]+/[a-z0-9_]+)/index\.htm$"  # bid = gdwx/hlm
catalog.item_selector = "a[href$='.htm']" ; id_from.pattern = r"^(?P<cid>\d+)\.htm$"
catalog.url_template  = "https://www.xuges.com/{bid}/{cid}.htm"
chapter.title_selector   = "td.t50"
chapter.content_selector = "td:not([class])"     # ← 纯 CSS 等价于「t50 之后第一个无 class 的 td」
```
实测《红楼梦》：目录 **279 项 → 归一化 277 章**；第 1 回正文 **16 段 / 2229 汉字**、标题正确。
✅ `<br>` 分段**本仓抽取器已原生支持**（`extract_paragraphs` 里有 `for br in container.find_all("br")`）——
即胡适日记项目手写的「get_text + splitlines」在这里**不需要重做**。

**⚠ 待解决：多页章回（古籍/文库站的通病）**
红楼梦目录里 `001` = `第一回…(1)`、`002` = 标题只有 `(2)`、`003` = `(3)` ——
**续页被当成独立章，且续页标题无内容**（末两章标题就是 `(2)`、`(3)`）。
→ 需要两个小能力（下一轮实施）：
1. **目录层合并续页**：标题匹配「纯 `(N)`」的条目**并入前一条**（不新增章）——
   目录页自己给了权威标记，优先用它；
2. **正文层续页判据** `next_page.continue_when: same_title_base`：
   剥掉 `(N)` 后标题相同才算续页。**这条不能省** —— 没有可靠停止条件时，
   跟着「下一页」会**一路把整本书拼成一章**。

**数据质量**：生僻字有 `\ufffd`（如 `曹頫` → `曹?`）。这是**站点侧**的损失（GB2312 装不下），
不是我们的解码问题 → **记录、不修**。

```
         POST /api/resource/list               {keyword…,pageNum,pageSize} → 书目 rows[]（id / coverPath / 题名 / 版本 / 藏馆）
② 书目   POST /api/anc/ancMetadataDetail/{id}                   → picArray[]（每页 filePath / fileName / imageId）+ ftpId
③ 册     POST /api/anc/ancStructureList?metadataId={id}         → 册列表（volumeTitle / fileNumber=页数 / ftpId）
④ 页图   GET  /api/common/jpgViewer?ftpId={ftpId}&filePathName={filePath} → **JPEG 位图**
```

⚠ **所有 `/anc/*` 与 `/resource/*` 都是 POST**（GET 会回 `Request method 'GET' is not supported`）；
检索的 body 必须是 `{type, advancedRetrievalParams, typeList, keyword, nameIndex}` 这套字段。
⚠ `/anc/ancMetadataDetail/{id}` 里的 `picArray` **只有 10 条（抽样！）**，
真实页数要去 **`ancStructureList` 的 `fileNumber`** 拿（本书 **2 册 / 62+67=129 页**）。

#### （3）实测数据

| 项 | 实测 |
|---|---|
| 页图 | **真 JPEG**，`3224×3009`，**3.3~3.8 MB/页**，2.3 s/页 |
| 整本体量 | 129 页 × ~3.5 MB ≈ **450 MB**（这本书不大） |
| OCR 引擎 | RapidOCR（onnxruntime），**5.2~5.7 s/页** → 129 页 ≈ 11 分钟 |

#### （4）⚠ 诚实评估：**OCR 质量不达标（抽样看约 6~8 成）**

页图是**双叶合拍**（`3224×3009` 横构图，一页图含左右两个半页）→ 整页 OCR 会把两个半页的行**交错串起来**。
**先切左右半页**（实测有效，行连通性明显改善）：

> 右半页识别：`故日混电至方未子初医新用明天始有根工营田那猴在山中夜宿石涯朝遂举桐真是山中无用子会初天氛下降地氛上升一派正合辈物皆生`
> 对照原文：`混沌未分天地乱，茫茫渺渺无人见。自从盘古破鸿蒙，开辟从兹清浊辨…那猴在山中，却会行走跳跃…夜宿石崖之下，朝游峰洞之中。`

逐字看：「混沌未分天地」✅、「自从盘古破鸿蒙」→「自旋盘古破」❌、「夜宿石崖」→「夜宿石涯」❌、
「天气下降地气上升」→「天氛下降地氛上升」❌。**错字集中在形近字与清刻本字形**。

**三条可执行的改进方向**（按性价比排序）：
1. **切半页**（已实测有效，先做）；
2. **按列切分**：竖排古籍可先按 x 投影切出**单列**再逐列识别，行序问题可根治；
3. ⭐ **用已接入的虚阁网同名书文本做后校对对齐** —— 虚阁网有《西游记》文本（P0 已接入），
   可用它做**字符级纠错**（形近字映射 + 上下文对齐）。**这是本项目独有的优势**：
   影印本 OCR + 文本版互校，比单跑 OCR 质量高得多。
4. 换更强的 OCR（PaddleOCR 竖排模型 / 商业 API）—— 但本机现成依赖是 RapidOCR。

**结论**：**P2 技术上完全可行且素材来源合法公开**（国图古籍库，`type=漢文古籍`）；
但要产出**可用**的古籍文本，还差「切半页 + 列切分 + 与文本版互校」这一步。
建议下一轮做这三项（都是纯本地处理，不再依赖外部站点）。

### 13.7 三条 OCR 改进的实测结果（v0.8.19）：**旋转 90° 是决定性的一条**

工具落地为 `tools/guji_ocr.py`（`search` / `info` / `fetch` / `ocr` / `eval` / `proofread`）。

#### （1）四档对比（同一批 8 页，用「行级最佳匹配」量，避免整体 ratio 在行序错乱时失真）

| 档 | 处理 | 行级字准率 | 识别总字数 |
|---|---|---|---|
| naive | 不切不旋，按 (y,x) 排 | 21.4% | 1418 |
| split | 切半页 + 坐标重排 | 24.1% | 1472 |
| colcut | 切半页 + 按 x 投影列切分 | 22.5% | 1472 |
| **final** | **切半页 + 逆时针 90° + 自动排序** | **26.5%** | **2952** |

#### （2）⭐ 真正的根因：RapidOCR 把**竖排当横排读** —— 排序救不了

诊断过程：先怀疑是**框顺序**问题（按 (y,x) 排 vs 按 x 降序排），但实测发现**排序改不了结果** ——
因为 RapidOCR 是**横排语料**训练的，面对竖排文本它会「**每列各取一个字**」组成一条横排「行」，
**分组本身就错了**。再排序也只是把错的组换个顺序。

**正解是「旋转 90° 让竖排变横排」**（古籍 OCR 的标准技巧）：实测**逆时针 90°** 最优 ——
`15.3% → 25.7%`（单页口径），全批 `21.4% → 26.5%` 且**识别字数翻倍**（1418 → 2952）。
转过来的文字**可读**了：「石碣上…一行楷…大字」「铁板桥」「花果山」「造化造化」
「须看三藏释尼传，欲知造化会元功」都对上了。

#### （3）⚠ 列切分在这份扫描件上**不成立**（诚实记录）

`_col_cut` 按 x 投影切列，实测**只切出 1 列（等于没切）**。诊断墨量 profile：
半页 `1612×3009`，**中位墨量 1760 / 3009（58%）**、5% 分位仍有 1154 → **几乎没有干净的列间白隙**。
原因：① 扫描件偏暗（灰度 mean 133）；② 有**版框/书边**导致整段满高；
③ 固定阈值 `g<160` 不适应。
→ 要让它生效需要 **Otsu 自适应二值化 + 先裁版框/黑边**。**本轮未做**（旋转已拿到主要收益）。
⚠ 这个教训值得记：**「列切分」听起来更"正统"，但对偏暗的实拍扫描件，旋转才是性价比最高的那条。**

#### （4）⚠⚠ 互校必须加护栏，否则会**静默抹掉影印本独有内容**

初版互校就是朴素做法：`OCR 串` 与 `参照串` 做 diff、**不同处一律换成参照的**。
实测**这是错的、而且有害**：
- 它把 `'像'` 整段改成 `'于绘画擅长书法爱好填词度曲对围棋也很'`（**不是纠错，是覆盖**）；
- 还把参照里 OCR 根本没有的内容（`∅→吴承恩约一说年字`）**插进正文**；
- 于是「匹配率 11.7% → **100.0%**」看着漂亮，实际等于**把参照文本抄了一遍**，
  而**影印本独有的内容（异文/批注/缺页补遗）被静默抹掉** —— 那恰恰是拿影印本的**唯一理由**。

**加护栏后的设计**（`tools/guji_ocr.py proofread`）：
- `replace` **只在长度差 ≤1 时**才当形近字纠正（`六`→`未`、`离`→`万`、`已年`→`巳午`、`有成六`→`酉戌亥`）；
- 长度差大的 `replace` → **保留 OCR 原文**，记为「对不齐，存疑」，**绝不覆盖**；
- `delete`（OCR 有、参照没有）→ **保留**，单独输出为「**影印本独有**」；
- `insert`（参照有、OCR 没有）→ **只记录不写入**（可能是 OCR 漏识，也可能是**版本差异**，不替读者决定）。

实测这套护栏：形近字纠正 **118** 处 ｜ 对不齐存疑 **81** 段（保留原文）｜
影印本独有 **14** 段（保留）｜ 参照独有 **44** 段（未写入）。

> ⭐ **一句话**：**互校的正确形态是「一对一形近字纠正 + 差异留档」，不是「向参照文本对齐」。**
> 一旦发现「匹配率涨到 100%」，那多半说明**已经把参照抄进来了**，影印本的价值归零。

#### （5）结论

| 项 | 判断 |
|---|---|
| 链路（检索→书目→册→页图） | ✅ **完全打通**，已封装成 `tools/guji_ocr.py` |
| 旋转 90° | ✅ **决定性增益**，已设为默认（`--rotate auto`） |
| 切半页 | ✅ 有效，默认开 |
| 列切分 | ⚠ 需 Otsu + 裁边才可能生效，本轮未做 |
| 互校 | ✅ 可用（**必须带护栏**），但**不能替代行序修正** |
| **OCR 绝对质量** | ⚠ **仍偏低**（粗估有效字准 4~6 成）。**根因是 RapidOCR 对清刻本字形能力有限** —— 想显著提升需换竖排专用模型（PaddleOCR 竖排 / 商业 OCR），**不是本仓几行后处理能补上的** |

### 13.8 OCR 模型选型实测（v0.8.20）：**瓶颈是行序，不是模型版本**

按全哥给的《2026 最硬核 12 个 OCR 开源项目》清单，结合本机条件做了选型实测。

#### （1）本机条件（决定了哪些"看着好"的其实上不了）

| 项 | 实测 |
|---|---|
| Python | `F:/Python314` = **3.14.7**（沙箱 3.13.14 无任何 OCR 依赖） |
| torch | **2.13.0+cpu**（⚠ **CPU 版**） |
| transformers | 5.15.1 ✓ |
| paddle / paddleocr | ✗ **未装**（Python 3.14 上 PaddlePaddle 基本无轮子） |

#### （2）PP-OCRv5 换模型实测：**确实更好，但增益小于版式处理**

本机 RapidOCR 用的是 **PP-OCRv3**（`ch_PP-OCRv3_det/rec_infer.onnx`）。
从 **ModelScope 的 `RapidAI/RapidOCR`**（396 文件 / 116 个 ONNX）下到官方 **PP-OCRv5 ONNX**：
`ch_PP-OCRv5_det_mobile/server.onnx`、`ch_PP-OCRv5_rec_mobile/server.onnx`、`ppocrv5_dict.txt`，
用改 `config.yaml`（含 `Rec.keys_path`，先备份、可还原）的方式换上。

> ⚠ `RapidOCR.__init__` 的 `config_path` 是**硬编码** `root_dir/config.yaml`；
> 字典走 **`Rec.keys_path` → `CTCLabelDecode`**。所以「改配置 + 备份/还原」比猜构造参数更稳。

| 口径 | naive(不切不旋) | v3（现行） | **v5 mobile** |
|---|---|---|---|
| 4-gram 命中率（**行序无关**） | 0.6% | 1.7% | **2.2%**（相对 +29%） |
| 3-gram 命中率 | 1.6% | 3.7% | **4.3%**（相对 +16%） |
| 行级最佳匹配（**对行序敏感**） | 21.4% | 26.5% | **27.1%** ← 只 +0.6pp |

**逐字比对能看出 v5 的真实进步**（同一段原文）：
- v5：`混沌未分天地` `自從盤古破鴻濛` `聞一元之氣有陰陽` ✅
- v3：`混沌**六**分天地` `自旋船古破浪缘骏` `陶一元之氣有险俱绘限之氛` ❌

> ⚠⚠ **方法论教训**：「行级最佳匹配」这个口径**测的不是"字认得对不对"，而是"整行能不能在参照里
> 定位"**，对**行序错乱极度敏感** → **把 v5 的单字提升掩盖掉了**（+0.6pp vs 4-gram 的 +29%）。
> **评估 OCR 质量时，要选一个"不依赖全局顺序"的口径**（n-gram 命中率 / 字符级 P/R），
> 否则会把真实进步误判成"没用"。
> 顺带：PP-OCRv5 的 **server 版在 CPU 上跑不完 8 页（>28 分钟）**，实际用只能选 mobile。

#### （3）⭐ 真正的瓶颈是**行序/版式**，不是模型

把三档放一起看，量级很清楚：

| 手段 | 4-gram 命中率 | 相对倍数 |
|---|---|---|
| 不切不旋 | 0.6% | 1.0× |
| 切半页 + 逆时针 90°（**版式处理**） | 1.7% | **2.8×** |
| 再把 v3 换成 v5（**换模型**） | 2.2% | 3.7× |

→ **版式处理带来的增益（2.8×）大于换模型（1.3×）**。而绝对值仍只有 2.2%，
说明**行序问题远未解决**（连续 4 字命中需要行内局部顺序正确）。
**结论：先解决版式（列序/行序），再谈换模型**；两者是相乘关系，不是替代关系。

### 13.9 ⚠⚠ 度量口径纠错 + C 的结论（v0.8.21）：**行序已基本解决，剩余误差在单字**

全哥定了「C 先做，再用 B 收尾」。做 C 的过程中，**发现我前面两轮的结论有一半是错的**，
根子在**度量口径错了两次** —— 这里如实纠正。

#### （1）我把度量搞错了两次

| 我用过的口径 | 实际测的是什么 | 为什么错 |
|---|---|---|
| 「行级最佳匹配」（§13.7） | **整行能否在参照里定位** | 对**行序**极度敏感 → 把 v5 的单字提升掩盖成 +0.6pp |
| 「4-gram 命中率」（§13.8） | **参照文本被覆盖了多少** = **召回率** | **分母是全书 5088 个 4-gram**，而 OCR 只覆盖一小段 → 2.2% 这个数**没有意义** |

**正确口径**：n-gram **precision**（分母 = **OCR 自身**的 n-gram 数），
并由 `p = 字准率^n` 反推**隐含字准率**：

| 档 | 汉字 | P1 | P2 | P3 | P4 | P5 | **隐含字准率**（P3/P4） |
|---|---|---|---|---|---|---|---|
| naive 不切不旋 | 1418 | 81.4% | 17.6% | 5.7% | 2.2% | 0.9% | **39% / 38%** |
| v3 切半页+旋转（现行） | 2952 | 79.5% | 18.9% | 6.7% | 3.0% | 1.3% | **41% / 42%** |
| v5_mobile 同上 | 3059 | 75.3% | 21.3% | 7.8% | 3.9% | 2.1% | **43% / 44%** |

→ 这个数与**目测的「4 成多」吻合**，且三档差异合理、可比较。**后面一律用这个口径。**

#### （2）C 的结论：**行序在旋转 90° 之后其实基本是对的**

直接 dump 旋转后 RapidOCR 的检测框（页 005 右半）：

```
检测框 13 个
  #   top     left    h      w      文字
  1   138     1237    156    1458   '石码七上二一行楷普大字端着花典山藤地水蟹道'
  2   282     1239    107    1441   '桐天石猴喜不自腾念頭国臂身跳战水来建锐'
  ...
框高 中位 116 ｜ 框宽 中位 1438 ｜ 高>宽 的框 0/13
y 范围 138~1492
```

**两个关键事实**：
1. **每个框 = 一整「列」**（宽 ~1440px），**按 `top` 排序就是正确的阅读顺序** —— 旋转 90° 之后
   RapidOCR 的**分组是对的**（这正是我们要的「列」）；
2. **框内文字顺序也对**：框 1「石码七上二**一行楷**普**大字**端着**花**典」
   ↔ 参照「…**一行楷**书**大字**镌着**花**…」—— 顺序一致，只是**个别字认错**（碣→码、镌→端着）。

→ 所以 **C 的核心（行序）已经由「旋转 90°」解决了**（§13.7 已实现并默认开启 `--rotate auto`）。
**不需要再做列切分** —— 旋转之后 RapidOCR 给的框本来就是「每列一个框」。
（也解释了为什么 `_col_cut` 那条路走不通也没关系：它想做的事，旋转已经做了。）

#### （3）修正后的总判断（推翻 §13.8 的一半）

| §13.8 我说的 | 实际 |
|---|---|
| 「瓶颈是行序，不是模型版本」 | ⚠ **一半错**：行序**已由旋转解决**；剩余误差在**单字识别**上（形近字、清刻本字形） |
| 「版式增益 2.8× > 换模型 1.3×」 | ⚠ 基于**错的口径**（召回率）得出，**作废**。用 precision 口径：版式 +2~3pp、换 v5 再 +2pp，**量级相当，都不大** |
| 「OCR 有效字准 4~6 成」 | ✅ 方向对，**精确定量是 41%（v3）/ 44%（v5）** |

**所以接下来的重点确实是 B（换更强的识别模型）**，因为 C 能做的（行序）已经做完了。

#### （4）DeepSeek-OCR 代码参考（全哥给的 zip）—— 两条可借鉴的

从 `DeepSeek-OCR-main` 里读到的有用信息：

1. **Gundam 多分辨率分块**：`base_size=1024, image_size=640, crop_mode=True`
   → **n×640×640 局部块 + 1×1024×1024 全局图**。这正是**密集小字（古籍）**需要的思路 ——
   先把页面切成小块提高有效分辨率，再整体感知版面。**我们的页图是 3224×3009，
   直接缩到 960 送 OCR 其实损失了分辨率** → 「分块送」可能是比换模型更便宜的提升点。
2. **`<|grounding|>` prompt 会输出坐标** → 用坐标还原阅读顺序。我们已有 RapidOCR 的框坐标，
   这条思路本仓已用上。

### 13.10 零下载实验：「分块送 / 提分辨率」实测**无效**（v0.8.22）

按「先试最便宜的、不够再换模型」的思路，先做了**不需要下载任何东西**的实验。
结论：**这条路可以正式关闭** —— 不必再考虑，直接上 VLM。

#### （1）「Gundam 式分块送」**照搬会破坏已有的正确分组**

看完旋转 90° 后的检测框就知道为什么：RapidOCR **已经把每一「列」各成一个框**
（页 005 右半：13 个框、框高 116 / 框宽 1438，按 `top` 排序即正确阅读顺序）。
再按 640px 切块，会把每条列**横向截断** → 分组反而变坏。
→ **它的形态与本素材不匹配，不能照搬。**

#### （2）它的内核（给检测器更多分辨率）也实测**只 +1pp**

Gundam 的内核是「给视觉编码器更多有效分辨率」。本流程里对应的旋钮是 **`Det.limit_side_len`**：
旋转后半页宽 **3009**，而默认 `limit_side_len=960` → 整幅被缩到 **0.32 倍**，
送检测的字只有 ~11px 高。把它调大就是等价做法。实测（同 3 页取样）：

| `limit_side_len` | 汉字 | P2 | P3 | P4 | **隐含字准率** |
|---|---|---|---|---|---|
| 960（默认） | 1245 | 19.6% | 6.7% | 3.3% | **42%** |
| 1600 | 1245 | 19.6% | 6.7% | 3.3% | **42%** |
| 3009（完全不缩放） | 1091 | 19.4% | 7.0% | 4.0% | **43%** |

→ **960 → 3009 只 +1pp，而且识别字数反而减少**（1245 → 1091）。
**分辨率不是瓶颈**（rec 阶段本来就是从原图按框抠图，未损失分辨率）。

#### （3）修正后的路线判断

至此，「便宜的先试」这一档**已经试完并且全部无效**：

| 试过的低成本手段 | 结果 |
|---|---|
| 切半页 | ✅ 有效（并入默认） |
| 逆时针 90° | ✅ **有效且是决定性的**（已并入默认） |
| 列切分 | ❌ 无必要（旋转后已是「每列一框」） |
| 4-gram/行级匹配 度量 | ❌ 口径错，已换 n-gram precision |
| 分块送 / 提检测分辨率 | ❌ **无效（+1pp）** |

**剩下的唯一变量就是「识别模型本身」** → **直接上端到端 VLM**。
顺序：**先榨干已在下载的 DeepSeek-OCR**（最强）→ 跑不动再降级到
**GOT-OCR2.0（1.37 GB）** 或 **HunyuanOCR（1.9 GB）**。

### 13.12 GOT-OCR2_0 打通并做了**严格对比**（v0.8.24）：**结论是「不划算」**

按全哥「按建议执行」→ 打通 VLM 路线 → 跑严格对比。**结论：VLM 在本素材上没有质变。**

#### （1）打通全过程（每一关都有证据）

| 环节 | 结果 |
|---|---|
| 权重 | ModelScope `stepfun-ai/GOT-OCR2_0` **1.37GB** ✓（断点续传脚本）|
| **CUDA torch** | ⭐ **装成** `torch 2.14.0+cu126`（主环境），`cuda.is_available()=True`，CUDA 12.6，RTX 3050 6GB |
| **GPU vs CPU** | ⭐ **37.8 秒 vs 17 分钟/页 → 快 27 倍** |
| **transformers 4.x 隔离** | 不建 venv（`F:/venvs` 写入被拦），改用 **`pip --target .sources/py4x`** + 脚本里 `sys.path` 前置 → **`transformers 4.57.6` 遮蔽主环境 5.15.1** ✓ |
| shim | 6 个全过：①`LlamaFlashAttention2`→`LlamaAttention` ②`is_torch_fx_available`→False ③`PretrainedConfig` 补 11 属性 ④`Tensor.cuda`恒等（CPU时）⑤`DynamicCache.seen_tokens` ⑥`DynamicCache.get_max_length`→None |

**⚠ `WinError 5 拒绝访问` 的真因（与那篇 cnblogs 文章讲的不是同一件事）**：
不是权限 —— 是 **`verovio` 在 cp314 上没有轮子 → pip 从源码构建**（失败路径里的
`lib/python/…` 就是 setuptools 构建目录）→ **构建期撞杀软文件锁**。
`verovio` 只是 GOT 支持**乐谱** OCR 的依赖，**去掉它立刻全过**（主环境已装真的 verovio）。

#### （2）⭐ 严格对比（同一批 8 页 / 同一 n-gram precision 口径 / **退化的也全部计入**）

| 档 | 汉字 | P2 | P3 | **P4** | **隐含字准率** |
|---|---|---|---|---|---|
| **GOT-OCR2_0（format）** | 1646 | 21.4% | 8.0% | **4.2%** | **44%** |
| RapidOCR v5 | 3059 | 21.3% | 7.8% | 3.9% | **44%** |
| RapidOCR v3（现行） | 2952 | 18.9% | 6.7% | 3.0% | **41%** |
| （参考）GOT 仅计 7 个**有效**半页 | 1509 | — | — | 4.6% | 45% |

**→ VLM 与 RapidOCR v5 基本持平（44% vs 44%），只比 v3 高 3pp。没有质变。**

> ⚠⚠ **必须记下的方法论教训**：我一度报出「GOT 54% vs RapidOCR 41%」——
> 那是**幸存者偏差**：只看了**单个半页**（232 字）且恰好是"好的半页"。
> **跑满 8 页、把退化的也算进去后优势就消失了。**
> **判据：OCR 质量对比必须「全量 + 含失败样本」，否则一定高估。**

**额外缺陷**：GOT **9/16 半页退化成重复串**（`清风清风…`/`猴王猴王…`/`我看看看…`），
多为**封面/题签/空白页**；RapidOCR **没有**这个问题。

#### （3）⭐⭐ 一条跨引擎的硬结论：**「版式预处理」不能照搬**

| 处理 | RapidOCR（逐**字**检测框） | GOT-OCR2_0（端到端 **VLM**） |
|---|---|---|
| 切半页（双叶合拍） | ✅ 需要 | ✅ **需要** |
| **逆时针 90°** | ✅ 需要（否则把竖排当横排读，字全乱） | ❌ **绝对不要**：字会**侧躺**，VLM 读不出 → **实测输出为空**（0 字）；不旋转后立刻给出 232 字可读文本 |

**判据**：逐字检测器靠「**框**」工作，字侧躺也能认 → 旋转有效；
端到端 VLM 靠「**看图理解**」，**字必须正立** → 旋转致命。

#### （4）最终判断

**VLM 路线（GOT-OCR2_0）在本素材上不划算**：
① 质量与 RapidOCR v5 **持平**（44% vs 44%）；
② 多出「退化输出」这一新缺陷；
③ 代价高（1.4GB 模型 + 隔离 4.x 环境 + 6 个 shim + 需 GPU）。
**→ 维持 §13.11 的决定：DeepSeek-OCR/HunyuanOCR 一并搁置**；若将来要再试，
**必须先确认语料变化**（换书/换刻本书型）能否让 VLM 拉开差距，否则不值得。

**本轮真正的净收获是环境与判据，不是 OCR 质量**：
CUDA torch 可用（27× 提速，其他项目也受益）+ 6 个跨版本 shim + 两条跨引擎判据。

#### ⭐ 投入前置条件（2026-09-21 **重写**；原判据有两处错，见下）

> **原判据（已废）**：「免费比例 < 5% 或需要登录 → 直接记存根，不投入」。
> **错在哪**：
> ① **免费章「数量」是站点策略（固定前 N 章），而比例 = N ÷ 总章数**
>    —— **书越长比例被稀释得越小，与「能不能做」毫无关系**

>    （云起书院 2.9% 免费却已接入，v0.8.5）。

| 轨道 | 通过条件（**两条都满足**） | 不通过时 |

实测火星小说免费章：页面 **1461 汉字，其中 0 个是正文**
（正文是注释里的一段 hex 密文）→ 只看汉字数会得出**完全相反**的结论。

1. **明文段落数**（含 ≥20 汉字的 `<p>`）**> 0** ← 最强指纹；
2. 无**长 hex 串**（≥120 字符纯 `0-9A-F`），**或**其 hex 解码后**熵显著低于 1.0**（= 只是编码，非加密）；

#### 火星小说 —— ⚠ **正文加密（hex 密文）** → 红线段，不做

> ⚠⚠ **本节留档一次我自己的误判与更正**（首版结论是错的）。

> 用 `probe_site.py` 新增的「正文真实性检查」独立复核，同样判「正文疑似加密」。

⚠ **域名先纠一个**：正版是 **`hotread.com`**（北京金影科技，title「火星小说|好看的免费小说网」），

| 项 | 实测（全部纯 HTTP，**零浏览器**） |

**② 「可读」必须用严格判据，不能用「页面汉字数」**：

→ 只认「**明文段落数（≥20 汉字的 `<p>`）> 0**」+「无高熵 hex 串」。
已做成机械检查：`tools/probe_site.py` **第 5b 步「正文真实性检查」**

#### ⚠⚠ 唯一卡点：正文有 686 个 PUA 码位 —— **先辨性质，再决定怎么处理**

产物终检首轮 **FAIL：残留 686 个 PUA**。**没有直接按「字体反爬」处理**，而是先查性质：

| 检查 | 结果 |
|---|---|
| 页面有 `@font-face` / 自定义字体吗？ | ❌ **完全没有**（也无任何字体 URL） |
| PUA 出现在哪？ | 古籍**缺字处**（与站点自己写的「（缺十一字）」「□□□」相邻） |
| 占比 / 码位数 | 686 ÷ 156094 = **0.44%**，**257 个不同码位**（真反爬是「**过半常用字**」的系统性替换） |

```json
"chapter": { "pua_fallback": "□" }
```

⚠⚠ **关键取舍**：**绝不能**做成「见 PUA 就替换」。若站点是**真·字体反爬**
